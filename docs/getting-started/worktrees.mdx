---
title: Worktrees and incremental builds
description: Share cached work while keeping Cargo and compiler state private
---

Run `kache init` once for your installation, then use ordinary Cargo commands in
each worktree. Worktrees using the same Kache store can reuse matching outputs
without configuring a remote. Start with the
[quick start](/docs/getting-started/quick-start) to verify that reuse.

## Keep a target directory per worktree

Leave Cargo's default `target/` in each worktree, or set a different
`CARGO_TARGET_DIR` for each concurrent build. Sharing Kache's artifact store does
not require sharing Cargo's fingerprints or writable compiler files.

A hit requires compatible source inputs, toolchain, target, features, and build
settings. A source edit or a different profile can miss. Cargo Fresh means Cargo
did not run the compiler; it is not a Kache hit.

If you already share one target directory, `kache cargo -- build` and
`kache cargo -- check` can separate each worktree's intermediate build directory
on Cargo 1.91+. The supported commands and exclusions are described in
[Concurrency limits](/docs/how-it-works/limits). Separate target directories
remain the normal setup.

## Three kinds of reuse

| Mechanism | What it reuses | What happens on an edit |
| --- | --- | --- |
| Artifact cache | Matching compiler outputs from the local store or a remote | Changed inputs can produce a new key and a compile |
| New-target seeding | Compatible registry/git dependency units already built in another checkout | Cargo checks the copied metadata and decides what is Fresh |
| Managed incremental state | Private compiler state for a unit being edited | rustc rebuilds the changed parts; this path is not an artifact-cache hit |

New-target seeding defaults to on through `cache.seed_new_targets`. It runs before
Cargo checks a new target reached through the Cargo shim. See
[New checkouts](/docs/getting-started/configuration#new-checkouts) for eligibility.

Adaptive incremental mode also defaults to on. After repeated compatible builds
of an edited unit, Kache can keep isolated incremental state instead of storing
each intermediate edit in the artifact cache. See
[Executables and incremental builds](/docs/getting-started/quick-start#executables-and-incremental-builds)
for the retry window and idle timeout.

With supported rustc 1.98+ layouts, `cache.seed_incremental` lets a managed
incremental compile import a compatible finalized session from another checkout.
Each receiver gets independent files or copy-on-write clones, never writable
hardlinks to the donor. Compiler feature probing and bootstrap behavior are
documented in
[Incremental seeds between worktrees](/docs/getting-started/mutation-testing#incremental-seeds-between-worktrees).
`kache explain --all` and `kache report` name the Cargo profile directory
each seeded compile imported from.

### Units of the shared tree

An edit is private to its checkout, but a pull or a rebase is not: every other
checkout builds the same sources, and one of them, or the store, may hold them
already. `cache.shared_ref` (default `origin/HEAD`, the upstream's default
branch) names the tree the checkouts share. A workspace unit whose package
holds what the merge base of `HEAD` and that ref holds, and none of whose
dependencies was compiled incrementally, keeps to the cache in a target with
incremental history too: Kache looks it up and restores it, or compiles it
whole and stores it while other checkouts that need it wait for that compile.
The unit's private incremental state is left as it is for the next edit.

A unit the branch changed, and everything built on it, compiles incrementally
([Kept units](#kept-units)). Git only picks the lane, never a cache key: when
Git is missing or cannot resolve the ref, every unit keeps the adaptive lanes,
and when it does not answer in time a kept unit stays kept. Set
`KACHE_SHARED_REF=off` or `[cache] shared_ref = ""` to turn it off.

### Kept units

A unit the checkout changed, and every unit built on one compiled that way,
keeps its incremental state for good (`cache.keep_incremental`, default
`private`): each compile starts from the last one's graph, with no count of
builds and no idle timeout ending it, and a cache hit, after a pull that
brings the shared tree back, leaves the graph for the next edit. Git is asked
about a unit without state only when its lookup missed, so a fresh checkout
restores what it can first.

A unit's first private compile imports a compatible graph from another
checkout. A build machine's folder that every change passes through can keep
every unit's graph for the others: with `keep_incremental = "all"` every
managed unit compiles on this lane, nothing of them is stored, and the
profile is recorded under the cache folder as a folder kept for others.
Receivers on the machine look in such folders before other checkouts, and
Kache's own clean-ups of unused graphs leave them to
whoever keeps the folder. A graph that does not fit is rejected by rustc,
which then compiles the unit whole: an import can cost a cold compile, never
a wrong build.

#### What a graph is worth on other libraries

A graph is worth what rustc can keep of it on the receiver's libraries. A
private compile maps the workspace where a stored compile does
(`/proc/self/cwd` on Linux, `/kache/workspace` on macOS; Windows keeps
`C:\src`), so a library's source paths are the same in both, but its crate
hash is not: with `-C incremental` rustc hashes the source spans of the
library's items into it, and every crate hash folds in those of the
libraries below. A library compiled on a kept lane is therefore another
build than the store's, and so is every library built on it. Measured with
rustc 1.99.1 on two crates, one built on the other, the dependent's own
graph reused against another build of the library:

| The library the dependent is compiled against | Instances compiled again |
| --- | --- |
| The build the graph was made against | 0 of 35,769 |
| Built in another folder, remapped to the same name (same crate hash) | 0 |
| Compiled with `-C incremental`, otherwise the same | 541 (the library's generic items) |
| Built in another folder, not remapped | 30,856 |

A library compiled incrementally costs little; one built with other source
paths costs far more. A real workspace mixes them, and a graph still pays
there. A build machine's folder that compiles every workspace crate
incrementally held 1,069 registry crates (of 2,970) whose crate hash
differed from the store's build of the same version and arguments; more
than half of them name a registry folder without the trailing separator
that the store's builds of it have. Two folders of one commit, filled hours
apart, held different builds of 412 of their 2,033 registry crates; why is
not known. A checkout's first edit of a base crate, with 197 private crates
above it, built in 31 to 72 s (median 40 s, three runs) with the graphs of
another folder at the same commit, though a median 13 % (by size) of each
graph's direct registry libraries were other builds than the checkout's.
Without the graphs it took 197 to 463 s, and compiled plain 158 to 196 s.
The same edit against the build machine's folder, at a newer commit, took 87
to 126 s, and 239 s without its graphs. The one loss seen was a test crate
built on 49 libraries: it compiled again 91 % of its 174,890 instances and
took 47.8 s, where no graph took 37 to 40 s.

So a receiver imports a graph whatever libraries it was made against, and
every seed records what its graph was made against: the metadata digest of
each `--extern`, whether the donor's checkout compiled that library
privately, and the `--out-dir`. Among the donors that published the graph,
one that wrote to the receiver's `--out-dir` goes first: the folder is not
part of a graph's key, but rustc compiles every codegen unit again when it
differs. Then comes one made against the receiver's libraries, apart from
those either checkout compiled privately (another build of the same crate),
then a folder kept for others, then the newest. An import made against
other builds of some libraries says `imported-other-libraries` in its
event, and `kache report` counts it. A seed from an older release has no
record and is imported as before.

A crate with [hidden compile-time inputs](/docs/getting-started/configuration#hidden-compile-time-inputs)
takes this lane too, and no other incremental lane. Kache completes Cargo's
dep-info with its inputs after every compile, so Cargo still runs the compile
when one changes, and rustc expands every macro again on each compile, so a
kept graph never serves a macro's old read of them.

These settings have separate purposes. Disabling `seed_incremental` stops donor
imports but keeps target-local adaptive compilation. Disabling
`adaptive_incremental` changes the edited-unit policy. Neither setting enables
[Blaze](/docs/getting-started/blaze).

## Inspect reuse and disk use

```bash
kache stats --last-build
kache explain
kache monitor
kache targets
```

In the monitor, select a build on Now, use Build for compiler events, and open
Why for recorded miss and bypass reasons. Cache hit counts exclude incremental
passthroughs and Cargo Fresh work.

The store holds identical output bytes once. Restores try copy-on-write clones,
then an artifact-specific hardlink policy or a byte copy. Writable metadata and
incremental seeds keep separate inodes. A target's logical size is not the extra
disk space it occupies. See [Deduplication](/docs/deduplication).

## Preview cleanup

```bash
kache clean --stale 14d --dry-run
```

Review the selected directories and freeable-space estimates before removing
anything. Running Cargo commands reached through Kache retain a target-use lease
so cleanup skips active targets. Keep that protection by leaving the Cargo shim
on PATH. For automatic policies and recorded-command unit cleanup, see
[Target directory cleanup](/docs/getting-started/configuration#target-directory-cleanup).
